# AOM Diagram Format Specification

> **⚙️ GENERATION ROUTE (mandatory since 25 Aug 2026):** this spec defines the visual format, but the file is never hand-written. The model lives in `[venture]-aom-model-at-C[N].yaml`; the HTML record and layered draw.io view are generated by the scripts in `.claude/skills/shared/generators/` (see each challenge skill's Section 6 for the run commands). Hand-edits to generated files are lost on regeneration.


Shared reference for all challenge skills. The AOM output is a single **Operational Model Map** built on a numbered 4-D component spine — not a table, and not big boxes joined by summary arrows. This spec defines the visual format, layout rules, and structural requirements. Challenge skills point here for format; they define their own process and venture-specific activity content.

## Mesh view design rules (IFC-derived — Simanis, "Running the Right Numbers: An Introduction to Operational Model Mapping", TIL Ventures)

The draw.io mesh view is generated to these rules. Structure comes from the IFC guide; shape/colour semantics come from the house style (the 2023 Calmly Lucid op model).

1. **Book-end the map** (guide, Step 3): the venture head office sits far LEFT; the end user / customer-side People (Customers · Users · Enablers-of-the-customer) adhere far RIGHT. Supply-side partners stack in a column between the venture and the flow items.
2. **Three vertical thirds** (guide, p.12): upper third = Marketing Information flows; middle third = Core Product components; lower third = Support product components and Production Information (which moves between middle and lower); Money flows cross all three but are drawn along the base. Generator strip rule: information-class flow carried by a CP → upper; product-class flow → middle; other information-class flow → lower; money-class flow → base.
3. **Arrows point at the receiving end only** (guide, p.12). No start arrowheads.
4. **Line medium**: dashed = flow moves digitally · solid = flow moves physically (guide, p.12). Default digital; a flow may declare `medium: physical` in the model YAML.
5. **Colour = flow class** (product red · information blue · money green), matching the item node's class.
6. **Spread nodes; one lane per flow**: every edge endpoint on a shared node gets its own anchor position (computed, evenly spaced per side) so flows never share a corridor.
7. **Narrative numbering**: items are numbered in transaction-cycle order (the spine), so the map tells time even though placement is by third.
8. **Shape semantics (house style)**: place = lavender rounded · person/partner = yellow hexagon · flow item = blue rectangle labelled `[component-id]` · money item = green trapezoid · org activity = pink rectangle · audit flag = amber note.
9. **Layout overlay (hand-composition is versioned, not lost)**: a sibling `[venture]-aom-layout-at-C[N].yaml` stores hand-arranged node positions by stable id; the generator applies it over the rule-based defaults, and page bounds follow the overlaid geometry. Harvest after arranging in draw.io/Lucid: `python3 .claude/skills/shared/generators/harvest_layout.py <view>.drawio`. New nodes have no entry and land at the rule-based default; delete an entry to return a node to the rules. Content stays in the model YAML — the overlay holds ONLY positions. Same mechanism serves the CTM drawio view.

## Format rules

The Operational Model Map is a single spatial diagram built on a **central spine of
numbered 4-D product component nodes**. This spine is the mandatory core. A map of big
boxes joined by summary arrows carrying two-line captions is **wrong** and will be
rejected — that is the failure mode of every rejected draft. Reference standard: the
Calmly "Op Model after C[n]" (Calmly Master File → Model, Simulate & Test).

**The components ARE flows, not static nodes.** Each traces the movement of the 4-D
product along the **HQ↔customer axis** — outbound (HQ → customer), inbound (customer →
HQ), or round-trip. Communications (marketing) are flows, not places. There are only
two poles — HQ and customer; partners are pass-through waypoints on a flow, never poles
of their own. A few money flows run HQ↔partner (funding in, levies and tax out) and
terminate at the partner rather than the customer.

**1. Scale header (top):**
- One line stating the last-mile operating unit and its scale, e.g.
  `LAST-MILE OPERATING UNIT: [N] units (bounded around [anchor]), each with a TRM of [X]`
  (TRM = target reachable market / at-scale volume per unit).
- **The LMU may be bounded by geography OR by customer segment** (Simanis: for digital
  offerings the LMU is bounded by "a defined customer segment"). Segment-served
  businesses (e.g. SME banks) bound by segment: a relationship pod sized by RM portfolio
  capacity for the larger customers, a digital service pod sized by service capacity for
  the mass segment. Both replicate independently; geography is only where pods are homed.
  If the financial model uses a different slice (e.g. 1/N of the national book), say so —
  the slice is a modelling construct, not the operating unit.

**2. Two poles only — everything between them is a flow:**
- **HQ pole** on the LEFT — the venture and its functions (credit & ops, digital platform, treasury, marketing) named inside one pole. Flows originate here.
- **Customer pole** on the RIGHT — the paying actor(s), named, with segments inside.
- **Partners are pass-through waypoints**, marked on the flow line that uses them (a credit agency on the onboarding flow, a scheme on the payment flow) — never a pole of their own. Off-axis partners (funding, tax, levies) sit in a partner band and connect to HQ by their own money flows.
- Poles and partners are ICONS (building / person), never plain rectangles. Distinguish People from Places.

**3. The component flows — the mandatory core:**
- Each component is ONE flow, drawn as a **directional arrow between the poles with its
  hexagon sitting ON the arrow**. Stack the hexagons top-to-bottom in the order they
  narrate the transaction cycle.
- Show **direction** with the arrowhead(s): outbound (arrow to the customer), inbound
  (arrow to HQ), or round-trip (arrowheads at both ends).
- Types & colours: **CP#** communications (blue) · **WP#** working (red/indigo) · **PP#** payment (green) · **PartP#** partner (purple). A **PartP** flow runs HQ↔partner, not to the customer.
- Number sequentially within each type (CP1, WP1, WP2, PP1…). Hexagon label: `[Code]#[N]`
  + a short flow description. NEW badge (amber) for flows added beyond the R1 baseline.

**4. Flows thread THROUGH the nodes — never summarised into arrow captions:**
- Three flow types as coloured lines: product/working (red) · information/communications (blue, dashed) · money (green).
- Draw the actual line: actor → component node → actor. A flow is a line, not a caption.
- Solid for primary flow; dashed for feedback / escalation.

**5. Cash in and cash out shown explicitly:**
- Every money inflow to the venture and every outflow from it is its own green flow,
  separate from the payment-product (PP) node — including outflows for losses, refunds,
  levies and partner fees (the money-outflow fidelity rule).
- **Bank/venture-boundary completeness check.** Beyond the customer axis and operating
  partners, three boundary actors ALWAYS exist and must appear with their flow pairs:
  **Shareholders** (equity in · dividends/returns out), **Employees** (labour in ·
  salaries out — usually the largest outflow), **Suppliers & vendors** (services in ·
  payments out). Also audit information OUT-flows (regulatory returns, data reciprocity
  to bureaus/partners, customer-permissioned API data). Close with a fidelity table:
  every P&L money outflow mapped to the flow that carries it.
- **Every flow carries a DRI** (one accountable owner, not a team) and a set of costed
  activities with [low, high] bands — or an explicit "costed via" note naming the pool
  or driver that carries its cost. A flow with no cost anchor and no DRI is incomplete.

**6. Legend and versioning:**
- Two legends: flow types (product/information/money) and component types (CP/WP/PP/PartP/NEW).
- Title the map by challenge state: `Op Model after C[n]`. Component codes are assigned as the design progresses.

**6b. Portfolio extension — mapping an EXISTING business (not a new venture):**
IVE's architecting process outputs ONE 4-D product (one CTM, one working product — e.g. the
microfinance group loan). An existing diversified business is not one 4-D product; it is a
**portfolio of 4-D products riding on a shared platform**. Forcing its product lines into a
single spine is the failure mode.
- **Model two layers.** (1) The **shared platform** — enabling channels, support products,
  partner rails, brand communications, and the back-office capabilities — serves every
  product. (2) The **product portfolio** — each product line is a full 4-D product with its
  own CTM, its own working product, and its own payment flows, drawing on the platform.
- **Working products are DERIVED from a per-product CTM — one WP per customer state change.**
  Never brainstorm WPs as a product catalogue. Build the product's CTM first (the state
  changes the product drives), then read the WP off it.
- **The state-change test sorts instrument from product.** Does this component drive its own
  customer state change? A *debit card* does not — it accesses the current account's state
  change, so it is an **enabling instrument** of that product. A *credit card* does — it
  drives "spend blocked by cash timing → spend enabled on credit", so it is its **own 4-D
  product** whose working product is the revolving line.
- On the map, group each product's flows into a **module** headed by the state change its
  CTM defines; shared-platform bands sit once, outside the modules.

**7. Capture the full range of flow (IFC guide — Simanis, "An Introduction to Operational Model Mapping"):**
- **Places may be virtual.** The app, online-banking site and payment platform are Places, not part of HQ — draw them as channels the flows route through.
- **Every product splits three ways: Core · Support · Enabling.** Core = the products themselves (accounts, loans, cards). Support = the whole-product experience (service, statements, complaints/disputes, contact centre). Enabling = what the customer needs to access the product (the app / online banking / authentication). Show all three, colour-coded within WP.
- **People split three ways: Customer · User · Enabler.** Customer pays; User uses (e.g. the SME's bookkeeper); Enabler's buy-in matters (e.g. the SME's accountant). Distinguish them on the customer side.
- **Line style encodes medium, colour encodes flow type.** Colour = product / information / money; **dashed = digital, solid = physical**. A digital payment is dashed + green.
- **Three role types per flow** (Step 4): direct producer · administrative support · managerial support. Tag all three in the Flow register; show at least the direct producer on the map.
- **Three-level layout:** marketing information along the top · core product in the middle · support product along the bottom; information moves between the middle and lower bands; money flows across all three.
- **BIAN completeness check.** Cross-reference the processes that move each flow against the BIAN Service Landscape (Reference Data · Sales & Service · Operations & Execution · Risk & Compliance · Business Support) so no capability is missed — especially the cross-cutting plumbing (reference data, product directory, entitlement / authentication, reconciliation, position keeping, clearing & settlement, sanctions / CDD, regulatory reporting, case & complaint management, collections & recovery, collateral administration, financial message gateway / Open Banking).

**Document structure (in order):**

1. **Operational Model Map** — the numbered component spine (Format rules above) — appears first
2. **Header** — venture name, at-scale volume, target LMU count, date
4. **Operating unit summary** — three cards: LMU / Territory / HQ
5. **Actor-first swimlane view (PRIMARY)** — LMU | Territory | HQ lanes; activities as cards within each lane; stream (Making/Selling/Marketing/Using) as a colour-coded label on the card, not a row header
6. **AOM matrix (SECONDARY — reference view)** — stream × level grid, labelled as reference only. Note: stream labels indicate activity type, not actor
7. **Activity detail table** — all activities with: Role · Activity · Level · Stream · Time per unit · Volume driver · Challenge tag (C1–C10) · Cost layer (PVC/RC/SC/IC)
8. **Cost stack summary** — four-layer table: PVC · RC · SC · IC → Required price · Target price · FMOS
9. **Working capital note** — WC to fill losses + WC for customer financing (separate)
10. **Routing panel** (navy) — handoff to fin-sim with Group 4 feed

**File naming:** `[venture]-aom-at-C[n].html` (Calmly example: `calmly-aom-at-C10.html`) — label by challenge, not version number.

## Activity volume driver discipline (critical)

> **VA-140 (Head of R&D, 16 September 2026, object-after 18 September 2026 17:00 BST) — a driver is a reference, never a sentence.** Ruling: `04-Projects/TMTH_Venture_Studio/R_and_D/rd-031-driver-as-reference-2026-09-16.md`. Until this date the `driver` field was free text and the checking script tested only that it was present. A rebuild of one venture's cost build in a driver-chain form found three drivers ending in a typed number with no counted event behind them and a count that matched its register by coincidence — none of it reachable while the driver was prose. Models dated on or after 18 September 2026 are refused for a breach; earlier models warn.

Every activity row must specify its volume driver — missing one is a hard stop. The driver answers one question: **what counted thing does this row scale with?** The answer is a reference the checking script (`validate_model.py`) resolves. Five clauses.

**(a) The driver is a reference to a named quantity in the model.** One of:

| Reference form | Resolves to |
|---|---|
| `quantities.<id>` | a base quantity declared in the model's `quantities:` block |
| `events.<id>` | an event declared in the model's `events:` block |
| `actors.<id>` | a counted actor in the roster |
| `components` · `build_components` · `controls` · `actors` | a register the model carries, meaning its size |
| `functions.<id>` | another function row's headcount (a row that scales with people) |
| `arm.<id>` | an input, derived quantity or activity id in the venture's resource model, when a `[venture]-arm-model*.yaml` sits beside the operating model |

A list of references is one driver with several parts. A mapping `{ref: <reference>, note: <text>}` keeps the sentence beside the reference. A bare word or a sentence in `driver:` is free text and does not resolve. Prose about the driver goes in `note:`.

**(b) An event carries `frequency` and a `parent` reference.** `events.<id>: {frequency: <number>, parent: <reference>, source: …, tier: …}`. Volume is frequency × the parent's volume, walked back until the chain reaches a base quantity or a headcount. An event never types its own volume, and the chain has no cycles.

**(c) A base quantity carries `source` and `tier`.** `quantities.<id>: {label, value | count_of, unit, source, tier}`. Tiers: **T1** a measured or published fact · **T2** counted from a register or record in the vault · **T3** a judgement by a named seat, recorded in a file · **T4** a typed number with no basis recorded anywhere. A T4 is legal and visible; a missing tier is refused.

**(d) A count that equals a register's size is written as the reference, never the number.** `count_of: components` (or `build_components`, `controls`, `actors`), not `value: 24`. A typed value equal to a register's size, on a quantity whose id, unit or label names that register, is refused.

**(e) A floor is declared, with a reason.** A row the design holds above its derived figure writes `floor: <number>` and `floor_reason: <text>`. The derived figure and the floor are then both visible. A floor asserted in `note:` or in the driver's words without `floor:` is refused.

The driver types below remain the vocabulary for choosing the reference; each one names the counted thing it scales with.

| Driver type | When to use | Written as |
|---|---|---|
| Per unit purchased | Happens once for every unit the venture commits to | a reference to the unit count (`quantities.<units>` or an event on it) |
| Per inquiry (pre-purchase) | Divide by conversion rate: 50% conversion = 2 inquiries per purchased unit | an event on the unit count with frequency 1 ÷ conversion |
| Per stage probability | Multiply by probability of reaching that stage | an event on the prior stage with the probability as frequency |
| Fixed per LMU / month | Amortise across monthly units | a reference to the LMU count, or to the venture as one entity (`quantities.<venture>`, value 1, T1) for a cost fixed at any volume |

No ratios ("X% of revenue", "1 per Y%"). Every cost traces to a named role + named activity + driver that resolves, by reference, to customer base, transaction volume or a register the model carries.

**What the checking script reports (VA-105).** Two lines on every operating-model validation: activity rows · resolved · unresolved (free text) · whether the rule is in force for the model's date; and events walked with the longest chain · base quantities by tier · floors declared · resource-model ids available.

## Partner business case — the side of the book (VA-147)

> **VA-147 (Head of R&D, 17 September 2026; Tom approved the registry row 21 September 2026) — a gateway partner sits on one side of the venture's effect, and a loss-side partner is priced against the pool it loses.** Ruling: `04-Projects/TMTH_Venture_Studio/R_and_D/rd-032-at-risk-pool-gateway-partner-2026-09-17.md`. On the loss side the architecture takes a pool the partner earns today; on the gain side the venture pays it a fee. The party that stands to lose the pool is the one to carry the product, and its price is the pool, never the status quo (this corrects VA-127's status-quo comparison for that actor). The preference is not a gate: a gain-side selection is admissible on one of five stated reasons, with its arithmetic. Models dated on or after 23 September 2026 are refused for a breach; earlier models warn.

Every partner actor (`class: enabler`, species `gateway` or `capability`; a `commodity_vendor` is exempt) whose `business_case` is stated carries `effect_on_book:` beside the five business-case fields (VA-99).

**(a) `effect_on_book` names the side and the signed amount.**

```yaml
business_case:
  earns: …            # the five VA-99 fields as before
  costs: …
  beats_next_best: …
  operational_fit: …
  timing: …
  effect_on_book:
    side: loss_side           # loss_side | gain_side
    amount: -420000           # a year; negative on the loss side, positive on the gain side
    source: R2 pool-at-risk block, typical incumbent
    tier: T3                  # T1 | T2 | T3 | T4, as for a base quantity
    pool_ref: conveyancer     # loss_side only — the incumbent id in the market model
```

**(b) A loss-side partner is bounded by the pool the market model states.** `pool_ref` names an incumbent row in the venture's market model `pool_at_risk:` block (`<venture>-tam-model.yaml` beside the operating model, or the file `market_model:` names at the top level). The amount may not exceed that row's `pool_a_year.high`. A loss-side partner with no sized pool row to point at is refused: the pool is the price, and a price with no pool behind it is the status quo comparison the rule removes.

**(c) A gain-side gateway chosen over a loss-side candidate states why.** Where a loss-side candidate is present — the market model states at least one incumbent pool, or another partner in the model sits on the loss side — a `species: gateway` partner on the gain side carries `reason:` on its business case:

```yaml
  reason:
    code: pool_below_cost_of_carrying     # one of the five below
    arithmetic: pool £180k a year against £310k a year to carry the product at scale
```

| `reason.code` | Meaning |
|---|---|
| `absent_from_routine` | the loss-side party is not in the customer's routine at the point of purchase |
| `fails_operational_fit` | the loss-side party cannot perform the partner product |
| `barred` | a rule or contract bars the loss-side party from carrying it |
| `pool_below_cost_of_carrying` | the pool is smaller than the cost of carrying the product |
| `lower_surplus_at_scale` | the gain-side party's surplus at scale is the larger, shown |

A code outside the list is not a reason; a code with no arithmetic is a label.

**What the checking script reports (VA-105).** One line on every operating-model validation: partner cases classified · loss side · gain side · unclassified · the market model read and the pool rows it carries · whether the rule is in force for the model's date.

## Four cost layers — all required

| Layer | Label | Contents |
|---|---|---|
| Product Variable Costs | **PVC** | Cost of goods per unit — upfront cash committed before revenue |
| Running Costs | **RC** | Labor (all delivery + selling + enablers) + general operating |
| Startup & Scaling Costs | **SC** | CapEx + Development & launch + customer acquisition cost |
| Investment Costs | **IC** | Debt cost + required return on equity; includes both WC types |

**Two WC types — keep separate:**
- WC to fill losses: cumulative operating shortfall during ramp → IC
- WC for customer financing: cash committed per unit × avg units in-flight → IC (often dominant)

FMOS gate uses all four layers. A gate run on only PVC + RC produces false positives.

## Fin-sim Group 4 feed (explicit handoff format)

At the end of any AOM update, produce this plain-text summary for the fin-sim:

```
FIN-SIM INPUTS FROM AOM — GROUP 4
Activity: [name] | Product: [CP/WP/PP/PartP] | Performer: [role] | Supporter: [role] | Driver: [per unit / per inquiry at X% / per stage Y% / fixed] | Time: [mins/unit]
```

One line per activity. This is pasted directly into the fin-sim session.
